### REV-001 No privacy policy or public account-deletion link anywhere in the app
- Dimension: Release readiness
- Severity: High
- Confidence: Confirmed
- Where: `src/features/profile/components/Profile/ProfileScreen.tsx` (no link), whole `src/` tree (case-insensitive search for `privacy`, `policy`, `terms of`, `openURL`, `WebBrowser` finds only the HC install URL at `src/shared/services/healthConnectSteps.ts:41` and `Linking.openSettings` at `src/features/nutrition/screens/BarcodeScannerScreen/BarcodeScannerScreen.tsx:144`)

Already an open owner item in `docs/PLAY_STORE_RELEASE_READINESS.md:74`; repeated here because it blocks release and has a code half.

- Suggested fix: Owner hosts both pages. Then add one "Privacy policy" and one "Delete account on the web" row to the Profile screen that call `WebBrowser.openBrowserAsync(url)`, with the URLs as constants (they are public). Trade-off: none beyond hosting.

### REV-002 Health Connect permission is requested at app start with no explanation, and the rationale entry point has no screen
- Dimension: Release readiness
- Severity: High
- Confidence: Confirmed (request path); Suspected (Play review outcome)
- Where: `src/shared/components/StepDisplay/StepDisplay.tsx:136-172`, `src/shared/services/healthConnectSteps.ts:25-37`, `src/features/nutrition/context/FoodContext.tsx:581-590`, `src/features/profile/utils/homeSurfaceEngine.ts:73-87`
- What happens: `FoodProvider` renders `StepDisplay` as soon as the signed-in stack mounts. Its mount effect calls `initialize()`, which calls `ensureStepsAccess()`, which calls `requestPermission([STEPS_READ])` when the permission is not yet granted. A new user therefore gets the system HC dialog on the first Dashboard render, before any in-app explanation. The explanatory Dashboard notice ("Track steps automatically ... Connect") is only shown after that dialog has been declined. The manifest's HC rationale and `VIEW_PERMISSION_USAGE` entries open the normal start screen (`docs/PLAY_STORE_RELEASE_READINESS.md:52,79`; there is no JS handling of those intents). The rationale screen is already on that checklist; the launch-time request is not.
- Why it matters: Play's Health Connect policy expects the permission to be requested in context and the rationale entry to show how data is used with a privacy policy link. Requesting at launch also uses up one of the prompts HC allows before it stops showing the dialog and the user must go to HC settings (platform behavior from general knowledge, not checked in this session). The iOS branch (`initializeHealthKit`) prompts at launch the same way.
- Suggested fix: On mount, only call `getGrantedPermissions()` and report `permission_denied` without requesting. Call `requestPermission` only from `retry` (the Dashboard "Connect" action), which already passes `userInitiated = true`. Change in `ensureStepsAccess`: add a `request: boolean` parameter and return `'permission_denied'` without calling `requestPermission` when it is false; pass `userInitiated` from `StepDisplay.initialize`. The rationale screen needs a small native intent check or a config plugin; until then, at least point it at the hosted privacy policy (REV-001). Trade-off: users who would have tapped Allow at launch now need one extra tap on the Dashboard notice.
- Effort: S (request timing), M (rationale screen)
- Needs device check: yes (HC dialog flow on Android 13 with the HC app and on Android 14+)

### REV-003 A missing production config value crashes the app at import with no screen
- Dimension: Release readiness
- Severity: Low
- Confidence: Confirmed (behavior); the trigger is a misconfiguration
- Where: `src/features/auth/services/firebaseConfigService.ts:28-30`, `src/shared/services/supabaseClient.ts:27-31`
- What happens: Both modules `throw` at module evaluation when `extra` values are missing. - Needs device check: no

### REV-006 Accounts created with Sign in with Apple cannot delete themselves
- Dimension: Security and privacy
- Severity: High
- Confidence: Confirmed
- Where: `src/features/profile/components/Profile/DeleteAccountModal.tsx:32-51`, `src/features/auth/services/firebaseAuthService.ts:132-174`, `src/features/auth/components/LoginScreen/LoginScreen.tsx:122-155`
- What happens: `usesPassword` is false for an Apple account, so `getCredential` always runs the Google sign-in flow and builds a `GoogleAuthProvider` credential. `reauthenticateWithCredential` then fails (`auth/user-mismatch` or a different-provider error) and the user sees "Choose the Google account you signed in with." or the generic failure. There is no Apple branch. Apple's token revocation on deletion is also not called (Apple requirement, general knowledge; not checked against current guidelines).
- Why it matters: Apple sign-in is offered on iOS (`usesAppleSignIn: true`, `app.config.js:41`). App Store guideline 5.1.1(v) requires in-app deletion for every account type; this is a rejection risk for the iOS build and a broken promise for those users.
- Suggested fix: Detect `providerData` `apple.com`, run `AppleAuthentication.signInAsync` with a fresh nonce (reuse `createAppleSignInNonce`), build `new OAuthProvider('apple.com').credential({ idToken, rawNonce })`, and pass it to `deleteAccount`. Hide the Google hint for Apple users. Trade-off: none; Android is unaffected.
- Effort: S
- Needs device check: yes (iOS)

### REV-010 Active-workout rows are keyed by position, so move and delete remount the rows below
- Dimension: Re-mounting
- Severity: Low
- Confidence: Confirmed
- Where: `src/features/workout/screens/StartWorkoutScreen/StartWorkout.tsx:335`, `src/features/workout/components/ExerciseInput/ExerciseInput.tsx:45-56,142-148`; same pattern at `src/features/workout/screens/WorkoutHistoryScreen/WorkoutHistory.tsx:127`
- What happens: `keyExtractor` returns `${exerciseName}-${index}`. Moving an exercise up or down, or deleting one, changes the key of every row after it, so React unmounts and remounts those `ExerciseInput` cards. Each remount replays the 250 ms card-entry fade (`cardEntry` starts at 0) and drops the focused text input and any note text typed but not yet blurred. History rows use `${monthYear}_${index}`, so finishing a workout (new item at the top) remounts every history card.
- Why it matters: Visible flicker during an active workout on exactly the actions that rearrange it, and a focused numeric field loses focus. No logged data is lost (sets live in `workoutService`).
- Suggested fix: Duplicates are already rejected by `isSameExercise`, so the identity is unique. In `StartWorkout.tsx` use `keyExtractor={item => exerciseIdentityKey(item.exerciseName, item.muscleGroup ?? '')}` (import from `../../utils/exerciseIdentity`). In `WorkoutHistory.tsx` use `keyExtractor={item => item.id}`. Required in the same change: the `SetRow` memo comparator (`src/features/workout/components/ExerciseInput/SetRow.tsx:492-513`) ignores `exerciseIndex`, `setIndex` and `handlePreviousSetPress`. Today that is harmless because a move remounts the rows; with stable keys a moved card would keep set rows bound to the old `exerciseIndex`, and edits would go to the wrong exercise. Add `if (prevProps.exerciseIndex !== nextProps.exerciseIndex || prevProps.setIndex !== nextProps.setIndex || prevProps.handlePreviousSetPress !== nextProps.handlePreviousSetPress) return false;` at the top of the comparator. Test: move an exercise, then edit a set in it and assert the right `workoutService` index is called.
- Effort: S
- Needs device check: yes (confirm the flicker is gone)

### REV-013 The Dashboard "today" nutrition card shows whichever date Nutrition last selected, and that date never rolls over at midnight
- Dimension: Correctness
- Severity: Medium
- Confidence: Confirmed
- Where: `src/features/nutrition/context/FoodContext.tsx:94,135-137,547`, `src/features/dashboard/screens/DashboardScreen/DashboardScreen.tsx:225,303,341-347`, `src/features/nutrition/screens/NutritionScreen/NutritionScreen.tsx:70`
- What happens: `dailyNutrition` in the food context is computed from `mealState`, which holds the meals of `selectedDate`. `selectedDate` starts as `new Date()` at provider mount and only changes through the Nutrition date picker. The Dashboard renders that value in `TodayNutrition` directly under a header that prints today's date. Two ways to get a wrong number: pick yesterday in Nutrition and go back to the Dashboard; or keep the app open (or backgrounded with the process alive) past midnight. In the second case Nutrition also keeps showing and adding to yesterday until the user picks a date. `useLocalDayKey` already exists for midnight and foreground refresh but is used only by Dashboard hooks, not by the food context.
- Why it matters: The main screen's calorie and macro numbers are for the wrong day with no indication, and after midnight new food lands on the previous day.
- Suggested fix: Two independent parts. (1) Dashboard: compute today's totals from the cache instead of `mealState`, for example expose `todayNutrition` from the provider as `calculateDailyNutrition` over `mealCache.current.get(todayKey)` keyed on `cacheVersion` and a `useLocalDayKey()` value. (2) Rollover: in `FoodProvider`, when `useLocalDayKey()` changes and `formatDate(selectedDate)` equals the previous day key, call `handleDateChange(new Date())`. Leave an explicitly chosen past date alone. This does not touch weekly evaluation timing. Tests: provider test with fake timers across midnight; Dashboard test with `selectedDate` set to yesterday.
- Effort: M
- Needs device check: yes (overnight background, then resume)

### REV-014 Dashboard and Food Selection show an invented 2,000 kcal target while the plan is still learning
- Dimension: Correctness
- Severity: Medium
- Confidence: Confirmed
- Where: `src/features/dashboard/screens/DashboardScreen/DashboardScreen.tsx:230`, `src/features/nutrition/screens/FoodSelectionScreen/FoodSelectionScreen.tsx:99`, `src/features/nutrition/context/FoodContext.tsx:157`, `src/features/nutrition/components/FoodSelectionHeader/FoodSelectionHeader.tsx:18,21`; contrast `src/features/nutrition/helpers/useDailyNutrition.ts:14-29` and `src/features/nutrition/components/NutritionStats/NutritionStats.tsx:63-73`
- What happens: During the learning phase `userMacros.targetCalories` is 0 by design and the Nutrition screen shows the learning ring with no target. The Dashboard replaces 0 with 2000 and shows "/ 2,000" and "N left"; Food Selection and `remainingCalories` (passed to Food Detail) do the same. `targetWorkouts` falls back to 5 the same way (`DashboardScreen.tsx:229`).
- Why it matters: The learning phase exists to measure what the user normally eats. Showing a fixed target on the home screen can steer intake during exactly that window and contradicts the Nutrition screen.
