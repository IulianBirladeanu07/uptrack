## New findings

### FUP-001 Registration still rejects an email with a trailing space
- Area: Correctness (REV-017 follow-up)
- Severity: Medium
- Confidence: Confirmed (code)
- Where: `src/features/auth/components/RegistrationScreen/RegistrationScreen.tsx:25,30,45`, `src/features/auth/utils/credentials.ts:3-4`
- What happens: `handleSignUp` calls `isValidEmail(email)` on the raw input. The regex `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` rejects any whitespace, so `name@mail.com ` shows "Please enter a valid email address." The trim in `signUpWithEmailAndPassword` is never reached. Login and password reset are fixed, because they have no format check before the service.
- Why it matters: Keyboard suggestions often add a trailing space, and the user cannot see it. Sign-up is the one screen where this blocks a new user.
- Suggested fix: Trim once at the top of the handler and use the trimmed value throughout. Add a test: type `'name@mail.com '` and assert the service is called with `'name@mail.com'`.

```tsx
  const handleSignUp = async () => {
    const trimmedEmail = email.trim();
    try {
      setLoading(true);
      if (!trimmedEmail || !password || !confirmedPassword) {
        setError('Please fill out all fields.');
        setLoading(false);
        return;
      }
      if (!isValidEmail(trimmedEmail)) {
        setError('Please enter a valid email address.');
        setLoading(false);
        return;
      }
      if (password !== confirmedPassword) {
        setError('Passwords do not match.');
        setLoading(false);
        return;
      }
      if (!isStrongPassword(password)) {
        setError('Password must be at least 8 characters long and include at least one uppercase letter, one lowercase letter, one number, and one special character.');
        setLoading(false);
        return;
      }
      await firebaseAuthService.signUpWithEmailAndPassword(trimmedEmail, password);
      setError(null);
      Alert.alert(
        'Registration Successful',
        registrationVerificationMessage(trimmedEmail),
        [
          {
            text: 'OK',
            onPress: () => navigation.navigate('Login'),
          },
        ],
        { cancelable: false }
      );
    } catch (error) {
      const err = error as { message?: string };
      const errorMessage = err.message || 'An error occurred during registration. Please try again.';
      setError(errorMessage);
    } finally {
      setLoading(false);
    }
  };
```

- Effort: S
- Needs device check: no

### FUP-002 The Dashboard learning badge is likely to overflow the card on narrow phones

### FUP-003 On iOS, HealthKit permission is still requested at app launch
- Area: UX, release readiness (REV-002 follow-up)
- Severity: Low while iOS is not shipped; Medium before an App Store release
- Confidence: Confirmed (code)
- Where: `src/shared/components/StepDisplay/StepDisplay.tsx:134-140,169`
- What happens: The mount effect calls `initialize()` with `userInitiated = false`. The Android branch now stops before requesting. The iOS branch always calls `initializeHealthKit(backend.kit)`, which shows the HealthKit sheet on first launch, before the user has seen why the app wants steps.

## Architecture and design notes on these commits

- **The fixes stay inside the existing structure.** New logic went into small pure helpers with tests (`calorieTarget.ts`, `buildExerciseRowKeys`) and shared components (`AuthScreenLayout`, `ErrorBoundary`). That's the right shape.
- **`FoodContext` grew again** to 36 fields (`todayNutrition`), and the provider now also runs the midnight rollover. That's consistent with ARCH-002; nothing new to fix.
- **"Today" is cache-only.** `todayNutrition` reads the meal cache for today's key. If today has not been loaded, for example after midnight while another date is selected, it shows 0 until the user opens today. Meals logged on another device show up only after the cache reloads. Both match how the rest of the context works, and ARCH-001 would remove the gap.
- **The merge write** (`22bfd9f`) also removes a read per meal save, which helps cost and the offline write path (REV-032).
- **The error boundary sits outside `NavigationContainer`.** Navigation state is lost on Restart, but Restart reloads the app anyway.

## Architecture and solution-design recheck (2026-10-25)

- **SYS-006 fixed:** `performEnhancedSearch` no longer returns up to 20 unrelated products matching only the first letter after similarity and full-name search fail. Search now returns an empty result. `NutritionHandler.test.ts` covers this behavior.
- **ARCH-001 and ARCH-002 remain real but are not urgent cleanup:** meal state still uses `FoodContext` plus its own persisted cache and write outbox, while workout/catalog reads use TanStack Query and other service caches. The meal outbox, profile reconnect and closed-history cache now have explicit recovery/invalidation behavior. A wholesale migration to Query would risk those guarantees without an immediate user-facing benefit. Migrate one read path only when it solves a concrete stale-data or reuse need; keep meal writes/outbox intact.
- **ARCH-003 remains coach-specific:** several workout read services still infer the signed-in uid. Make subject uid explicit before adding cross-user coach reads, not as a broad preparatory refactor.
- **ARCH-004 and ARCH-006 are acceptable for the current single-user product:** the user document combines profile and progress fields, and there is no trusted server tier. Do not open cross-user reads or trust a client-written role. If coaching is pursued, decide exactly what data a coach may see and whether coaches are verified before implementing the proposal.
- **ARCH-005:** the bottom bar still navigates within a native stack, but its controls now expose tablist/tab accessibility semantics. A nested tab navigator is a coordinated React Navigation upgrade, not a standalone fix; defer until the next navigation or coach feature work.
- **ARCH-007 is partly superseded:** Firestore still has only the JS SDK's in-memory read cache, so offline historical reads are not durable. Meal writes now use a durable per-user outbox, workout completion retains/retries its active session, and profile data refreshes on reconnect. This does not justify migrating every service to the native Firebase SDK unless offline read access becomes a product requirement.
- **SYS-005, SYS-007 to SYS-009 remain operational choices:** reproducible backend indexes/functions need console export and owner review; iOS release automation matters only if iOS is a target; OTA and production-build workflows need an explicit release-process decision. No live backend, build, deploy or publish action was taken.
- **Coach solution design is a proposal, not an approved feature:** the main remaining work is product decisions (coach verification, consent scope, visible data, read-only vs writes, account types and offline behavior). Do not start the proposed sharing rules or schema migration before those are decided and the health-data privacy language is reviewed.
